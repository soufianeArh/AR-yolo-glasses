## Step 4: Java scheduler v1, with one worker and a fake client ✅

**Goal:** the full backend path working end to end.

Installed in WSL: OpenJDK 21 (~300 MB), Gradle 9.9.1 (wrapper in `scheduler-java/`),
gRPC-Java 1.85.1 + protobuf 4.36.2 (~400 MB in `~/.gradle`), OpenCV for Python in `~/ar-venv`.

Done: `scheduler-java/` (Java 21, plain grpc-java, virtual threads, 0 compiler warnings)
- **One port** (default 50051) serves both `FrameStream` (Android app) and `WorkerControl`
  (worker heartbeats).
- **Workers register themselves** with their first heartbeat; unhealthy after 3 s of silence,
  healthy again when heartbeats resume. The scheduler connects to a worker as soon as it
  registers, and reconnects immediately (skipping gRPC's back-off) when heartbeats resume.
- **Per frame:** pick the healthy worker with the fewest frames in flight, call it with a
  **300 ms** gRPC deadline, send the result back on the same stream. Non-blocking: worker
  calls are async. A session closes only after every pending result went out.
- Status mapping: deadline → `DROPPED_DEADLINE`; worker queue full → `NO_WORKER`
  (no retry in v1); worker error or crash → `WORKER_FAILED`; no worker → `NO_WORKER`.
- Device token read from the `authorization` header (recorded, not checked yet).
- Throughput, status counts and backend p50/p95/p99 logged every 5 s.

`tools/fake_client.py`: the fake Android app (plays `loop.mp4` pre-encoded as ~640 px JPEG,
8 fps, max 1–2 frames in flight, drops frames on the client when full). `images` mode sends
files one by one and prints JSON results.

**Test** (`tools/test_scheduler.py`, real scheduler + real C++ worker with 4 threads), 2 runs
after the fixes: run 1 **14/15**, run 2 **15/15**.
- ✅ No worker → `NO_WORKER` without hanging; the worker registers through its heartbeat.
- ✅ **Results through the scheduler identical to `worker-cli`** (12 images, 23 detections).
- ✅ Worker killed → the next frame is answered `WORKER_FAILED`, the worker is marked unhealthy,
  then `NO_WORKER`; the scheduler keeps running. Worker restarted → OK again. Clean shutdown.
- ⚠️ "≥95% OK with 1 frame in flight": 100% in one run, **89% in the other**. Not a code bug:
  the CPU throttles and single inferences then take up to ~300 ms (p99 306 ms), right at the
  deadline. To be settled in Step 5 (threads per worker, or a ~400 ms deadline).

Measured (one worker, 4 threads, everything on one machine, so no Wi-Fi in these numbers):

| | 1 frame in flight | 2 frames in flight |
|---|---|---|
| OK throughput | 3.3–4.0 fps | 6.1–6.7 fps |
| Client latency p50 / p95 | 147–160 / 178–250 ms | 218–232 / 280–295 ms |
| Dropped at the 300 ms deadline | 0–11% | 4–7% (once 20% before the fixes) |
| Scheduler overhead on top of inference | 7–96 ms | |

Bugs found by the test and fixed: (1) the first frames expired because the scheduler only
connected to a worker on its first frame (~250 ms); (2) after a worker restart, gRPC's
reconnect back-off failed the first frame.

## Step 5: Java scheduler v2, with N workers (the scheduling core) ✅

**Goal:** real scheduling, load balancing and failover. This is the Java and HPC heart of
the project.

Installed in WSL: JUnit 6.1.3 (Gradle), matplotlib in `~/ar-venv` (venv now ~370 MB).

Done:
- **C++ worker aborts an inference halfway when its deadline passes** (ONNX Runtime
  `RunOptions::SetTerminate`, from a watcher thread polling every 5 ms). The CPU goes back to
  live frames instead of finishing answers nobody waits for. 125–216 aborts per test run.
- **Load estimate is now accurate:** the scheduler's in-flight count drops at the deadline at the
  same moment the worker stops computing (thanks to the abort).
- **Routing:** least frames in flight; on a tie, the worker picked longest ago (idle workers take
  turns). Pick and reservation are one atomic step, so simultaneous frames don't pile on one worker.
- **Retry:** on `RESOURCE_EXHAUSTED` (queue full) or `UNAVAILABLE` (unreachable), one retry on
  ANOTHER worker, only if at least 50 ms of the deadline is left. Never on `DEADLINE_EXCEEDED`.
- **Immediate suspension:** a worker found unreachable gets no new frames at once, instead of
  after the 3 s heartbeat timeout; its next heartbeat makes it healthy again.
- **Per-session cap: 2 frames in flight** (`--session-max-in-flight`). More → answered at once
  with the new contract status `SESSION_LIMIT` (added to `detection.proto`, a safe change).
  Cap 4 was tried first and let a misbehaving client starve a normal one.
- Per-worker frames-per-window and retries in the 5 s log line.
- `scripts/start-workers.sh N THREADS` / `scripts/stop-workers.sh`.

**Tests** (all rerun at the end of the step):

| Suite | Result |
|---|---|
| `tools/test_scheduler_v2.py` (Step 5, end-to-end) | **18/18** |
| `tools/test_scheduler.py` (Step 4, regression) | **15/15** |
| `tools/test_worker_server.py` (worker + abort check) | **16/16** |

Step 5 end-to-end covers: 3 workers register; **3 sessions at once get exactly the
`worker-cli` results** (correctness tested with a 5 s deadline, so speed can't interfere);
load spread over all workers (busiest/least busy ratio 1.09–1.14); a misbehaving client gets
`SESSION_LIMIT` while a normal client next to it stays OK; queue full → retried on the other
worker; **worker killed mid-stream → 0 `WORKER_FAILED` / `NO_WORKER` reach the clients**, the
worker is suspended at once, the others take over, and it gets frames again after a restart.

**Benchmark** (`tools/bench_scheduler.py`, ~10 min; results in `bench/summary.md`,
`bench/results.json`, graph `bench/throughput.png`). 8 fps per session, max 2 frames in flight,
deadline set to 1 s so real latencies are measured, 2 repeats (second in reverse order), median:

| Workers × threads | 1 session: OK fps, p95, ≤300 ms | 2 sessions: OK fps, p95, ≤300 ms / ≤400 ms |
|---|---|---|
| 1×4 | 7.2 fps, 309 ms, 94% | 7.8 fps, 413 ms, 22% / 56% |
| 1×6 | 6.8 fps, 128–626 ms (unstable), 82% | 7.9 fps, 525 ms, 30% / 55% |
| 2×2 | 7.8 fps, 229 ms, 99% | 9.5 fps, 435 ms, 15% / 81% |
| 2×3 | 7.8 fps, 220 ms, 99% | 9.9 fps, 501 ms, 34% / 92% |
| **3×2** | **7.8 fps, 246 ms, 99%** | **10.9 fps, 383 ms, 74% / 96%** (most stable) |
| 4×1 | 5.3 fps, 344 ms, 81% | 9.4 fps, 495 ms, 4% / 83% |

Conclusions:
- **The machine's ceiling is ~11 frames/s in total** (4 physical cores). More workers than that
  only make each inference slower (250–300 ms each with 3×2 under full load, vs ~145 ms alone).
- **Best setup: 3 workers × 2 threads** (`bash scripts/start-workers.sh 3 2`).
- **One session (one pair of glasses, 8 fps) fits the 300 ms deadline** (99% of frames).
- **Two sessions don't fit 300 ms on this laptop** (16 fps asked, ~11 possible): 74% in time,
  96% with a 400 ms deadline.
- Big single workers (1×6) vary the most between runs (CPU heat).
- All on one laptop: the fake clients and test tools share the CPU; no Wi-Fi in these numbers.

**Open decision:** deadline 300 ms (one pair of glasses per laptop) or 400 ms (two pairs, 96%).

## Step 6: Python control plane ✅

**Goal:** alerts and history, off the hot path.

Installed in WSL: Redis 7 and PostgreSQL 16 (`apt`, ~185 MB, started automatically by systemd);
Postgres role `ar` (password `ar`, local development only) with databases `ar` and `ar_test`;
FastAPI, Uvicorn, SQLAlchemy 2, Alembic, psycopg 3, redis-py, pytest, httpx in `~/ar-venv`
(now ~480 MB); Jedis 8.0.2 in the scheduler.

Done:
- **Scheduler → Redis Stream `ar:results`:** a copy of every result (protobuf `FrameResult` +
  device id + receive time). **Never blocks the fast path:** results go into a 10,000-entry
  memory buffer and one background thread writes them to Redis in batches. Redis down → results
  wait in the buffer and go out when it is back; buffer full → oldest dropped (counted). The
  stream keeps ~100,000 entries. `--redis none` turns publishing off.
- Session ids now unique across scheduler restarts; devices identified by a hash of their token
  (`dev-xxxxxxxxxxxx`), never the token itself.
- **`control-python/`:**
  - **Consumer** (`python -m ar_control.consumer`): Redis consumer group; one Postgres
    transaction per batch; acknowledges only **after** commit (at-least-once delivery) and a
    unique `(session_id, frame_id)` stores each result once. Recovers its pending entries after a
    crash; recreates its group if Redis restarted empty; skips (and counts) malformed entries.
  - **Rule engine:** threshold → quorum → cooldown, per **(rule, device)**, using the time the
    frame was **received** (a backlog after an outage raises the same alerts as live).
    Alerts in a batch only count once the transaction commits. Cold start reads the last alert
    from the database, so a restart doesn't re-announce everything in view.
  - **API** (`uvicorn ar_control.api:app`, separate process): `/rules` CRUD with validation,
    `/alerts` (+ idempotent `/ack`, `/summary`), `/detections`, `/stats` (status counts,
    latency percentiles, per-worker share), `/health` (database, Redis, consumer pending/lag).
  - **Migrations:** Alembic (`migrations/versions/0001_initial.py`), tested down and up.
- `/config` (models, thresholds) **not built**: nothing reads it until the Android app's settings
  exist. Moved to Step 8.

**Tests** (all rerun at the end of the step):

| Suite | Result |
|---|---|
| `tools/test_control_plane.py` (Step 6, full chain) | **15/15, twice** |
| `control-python/tests` (rules, consumer, API, migrations; pytest) | **19/19** |
| `tools/test_scheduler_v2.py` (Step 5, regression) | **18/18** |

Full-chain results (3 workers × 2 threads, test Redis on port 6390, database `ar_test`):
- **Alerts:** 6 cow frames inside a 5 s cooldown → **exactly 1 alert** (cow ×4, max conf 0.888).
  Stored detections identical to `worker-cli`.
- **Redis killed mid-stream** (restarted empty 4 s later): fast path 97–99% OK (p95 230–246 ms vs
  233–242 baseline); **all 92–94 frames still reached Postgres** from the scheduler's buffer.
- **Consumer killed (SIGKILL) mid-stream**, restarted 4 s later: **79/79 frames stored**, pending
  and lag back to 0. Fast path compared with a control run without the crash: 100% vs 99% OK
  and 96% vs 100% OK, so the crash had no visible effect.

Tests fixed during the step (they mixed timing with logic and failed once the CPU got hot):
correctness checks now resend frames that missed the deadline before comparing; failover
allows `WORKER_FAILED ≤ 2` (frames on the killed worker with < 50 ms left can't be retried, by

measurement.

2 sessions got only ~24% of frames within 300 ms (74% in the cooler Step 5 benchmark), and a
normal client next to a heavy one fell to ~25% OK (96% alone). The cap guarantees no client is
refused; it can't prevent the shared CPU from slowing everyone. For long demos: one pair of
glasses, a 400 ms deadline, or a machine with real cooling.

## Step 7: Plant-disease detection in the backend

**Goal:** the C++ workers detect **leaf diseases** (corn, tomato, potato...): this is the core
goal of the detection part. COCO YOLOv8n (cows, people) was only a placeholder to build and test
the pipeline in Steps 2–6; it stays as a fast pipeline test.

**The model:** soufiane-easy's `plant` model, YOLOS-small trained on PlantDoc: **30 classes over
13 crops**, e.g. `Corn leaf blight`, `Corn rust leaf`, `Corn Gray leaf spot`,
`Tomato Early blight leaf`, `Tomato leaf late blight`, `Tomato Septoria leaf spot`,
`Tomato leaf mosaic virus`, `Potato leaf early blight`, `Potato leaf late blight`, plus healthy
leaves (`Tomato leaf`, `Potato leaf`...). Known behaviour (from soufiane-easy's own tests):
- no healthy-corn class → a healthy corn leaf can be called `Corn leaf blight` (0.70);
- tomato blight is often reported as `Potato leaf late blight` (same pathogen);
- scores run lower than COCO's → its own confidence floor (0.40 in soufiane-easy);
- **the leaf must fill the frame**: lesions are millimetres wide. It is an **inspection** job,
  not something seen from a distance while walking.

**Why it needs work:** it is a **transformer** (YOLOS, loaded with `transformers`), not a
YOLOv8 network, so the current C++ detector can't run it, and it is **heavier** (bigger input,
estimated 0.5–2 s per image on this CPU, to be measured): it can't fit the 300 ms live stream.

**How the wearer uses it: "look and hold" first.** The wearer looks closely at a leaf and holds
still for a moment; ONE frame goes to the plant model with a longer deadline (~2 s); a popup
shows the result, e.g. "Tomato late blight 0.87". Continuous checking comes later, once a fast
model is trained (7.6).

### Step 7 results (7.1–7.5 done)

Installed: `transformers`, `onnxscript` in `tools/.venv` (Windows). The plant model is copied to
`models/plant-disease/` (120 MB, not in git) and exported to `models/plant.onnx`.

- **7.1 Test material:** `testdata/plant/` = soufiane-easy's 6 samples + 39 PlantDoc TEST images
  (3 for each of 13 corn/tomato/potato classes), expected labels in `expected.json`;
  `testdata/plant/videos/` = 3 look-and-hold videos (corn, tomato, potato; 24 fps, 1280×720; the
  view moves with motion blur, holds 2 s on a leaf, moves on) + `*.timeline.json` (hold windows and
  expected disease). Tools: `tools/make_plant_videos.py`.
- **7.2 Export** (`tools/export_plant_onnx.py`): dynamic height/width (the model takes a different
  size per image: short side 512, long side ≤ 864, multiple of 16), checked against PyTorch at every
  test size; class names and preprocessing written into the ONNX metadata.
  **Speed fix:** the model resizes its position embeddings with bicubic interpolation, which ONNX
  Runtime ran extremely slowly (3.6 s of ~5 s; one 3.3 s node that also delayed aborts by ~2 s).
  Exported instead as two small matrix multiplications with the same math
  (`tools/bicubic_matmul.py`, equal to PyTorch within 1e-6): **6.1 s → 1.9 s** per inference
  (2 threads), **abort 2 s → 7 ms**.
- **7.3 C++:** `YolosDetector` (`worker-cpp/src/yolos_detector.cpp`): a port of transformers'
  preprocessing, including torchvision's **antialiased fixed-point resize** (pixel-identical on
  14/15 test images, ±1 level on 0.25% of pixels in an extreme 5× shrink), softmax over 31+1
  classes, no NMS. Both detectors now share `OrtModel` (`ort_model.cpp`: loading, metadata,
  run with abort). `load_detector()` picks the type from the model file (`--model-type` to force).
- **7.4 Speed** (one worker, ~640 px frame): 1 thread 3.4 s, 2 threads 1.9 s, **3 threads 1.6 s**
  (p95 1.8 s), 4 threads 1.6 s, 6 threads 1.4 s. **CPU split** (`tools/bench_plant_split.py`,
  `bench/plant_split.json`): running a plant inspection every 2.5 s DURING a COCO stream breaks
  both on this 4-core laptop (COCO 0–61% OK, plant 2.8–4.7 s). → **Plant only**: 1 plant worker ×
  3 threads; COCO only for pipeline tests, not at the same time.

## Step 8: Android app on the emulator, shaped like the glasses ✅

**Goal:** the real client, built and tested on the Android emulator configured to act like the
glasses. **No phone step** (decided 2026-11-17): the phone was only ever a stand-in for the
glasses, so the app goes from the emulator straight to the glasses in Step 9.

**Before starting** (checked 2026-11-17):
- Android Studio + SDK installed (Android 29–34, build-tools 34, Android 14 x86_64 system image).
  No download needed for the emulator itself; the Android build libraries need ~1–1.5 GB
  (16 GB free).
- **Network (corrected 2026-11-18, found in 8.2):** `10.0.2.2` does **NOT** reach the backend on
  this Windows 10 PC. The emulator reaches Windows' **IPv4** localhost through `10.0.2.2`, but WSL's
  relay only listens on **IPv6** localhost (`::1`), so the connection stalls. (The earlier "verified"
  check used Redis and passed for another reason.) **Working route, no admin needed: WSL's own IP**
  (`wsl hostname -I`, e.g. `172.22.36.122`; it changes after a reboot), given to the app at launch:
  `adb shell am start -n com.soufiane.ar.glasses/.MainActivity --es host <WSL IP> --ei port 50051`
  (the settings screen in 8.6 makes it permanent). Alternative with admin rights: a Windows
  `netsh interface portproxy` from `127.0.0.1:50051` to WSL - needed for the glasses anyway (Step 9).
- **The backend must run in a WSL session that stays open:** WSL shuts down (and clears `/tmp`)
  when no session is attached, killing what `start-backend.sh` started in the background. Run it
  from a WSL terminal and keep that terminal open.
- **RAM (8 GB laptop) is the main risk:** WSL ~4 GB + Android Studio ~2 GB + emulator ~2–3 GB.
  Give the emulator 2 GB, close Chrome, and run a light backend while developing (few workers).
  If still too slow, cap WSL's memory (`.wslconfig`).
  **Measured in 8.1–8.2:** the emulator alone takes ~2.9 GB; with the backend and a plant
  inspection running, Android's own System UI became unresponsive ("isn't responding" dialog).
  Working order that never runs all three at once: **close the emulator → build the app (Gradle
  needs ~1.5 GB) → stop Gradle (`gradlew --stop`) → start backend + emulator → install → test.**
  Idle Gradle daemons (also the scheduler's, inside WSL: ~1.4 GB) must be stopped. Close IntelliJ
  and browsers before starting the emulator.

**Make the emulator act like the glasses:**
- A virtual device with the glasses' screen: landscape, the chosen Goolton model's resolution
  (until the model is chosen: 1920×1080 landscape).
- **Designed for a see-through display:** on optical AR glasses black pixels are transparent, so
  a black background with only a bright, high-contrast popup in the top-right corner.
- **Low minimum Android version** (e.g. Android 8–9): the Android version under WEBB OS is
  unknown, and the app must install there.

**What the app does** (seen from the wearer):
- **Main mode: plant inspection ("look and hold").** The wearer looks at a leaf and holds still;
  the app sends that frame to the plant model; a popup in the top-right corner shows the result,
  e.g. "Tomato late blight 0.87", or "Healthy leaf". A small indicator shows "checking...".
- **Pipeline test mode: COCO stream.** Continuous detection of `person, cow, sheep, horse, bird,
  dog` (8 fps): used to test the streaming pipeline, not the goal.
- A fully black screen otherwise (see-through on the glasses), a small status dot (connected /
  reconnecting / no server), a settings screen.

Behind the scenes: take a frame → shrink it, JPEG → send it to the Java scheduler over gRPC with
the model to use (`plant` or `default`) → get the detections back → decide what to show. At most
1–2 frames in flight; new frames are dropped while busy.

**Where images come from on the PC:**
- **`FileSource` (main test source):** the app plays a video or images as if they came from a
  camera, so the expected detections are known:
  - **plant material from Step 7.1** (diseased and healthy leaves, panned/zoomed videos);
  - **moving farm footage** in `testdata/moving/` (free Mixkit clips, 24 fps, 1280×720), for
    the COCO stream: `couple-walking-among-cows-41565.mp4` (2 `person` every second + 1–5

  - `loop.mp4` (from soufiane-easy) is a slideshow of still photos: known images only, no motion.
- **The PC webcam (`CameraXSource`, 8.7):** the emulator can use the webcam as its camera. Hold

- Restart only the scheduler (workers keep running and re-register):

- Shell scripts must keep Unix line endings (`.gitattributes`); a CRLF `start-backend.sh` fails with

## Step 9: Moving to the glasses

**Goal:** the same Android app on the Goolton glasses. This is the **first real-world test**
(camera, Wi-Fi and hardware at once), since there is no phone step.

**Before starting:**
- The glasses can't reach the backend inside WSL directly (WSL2 NAT on Windows 10). On Windows,
  forward the Java scheduler's port into WSL (`netsh interface portproxy`) and allow it in
  Windows Firewall: one-time setup, needs admin. WSL's IP changes on every reboot, so the
  forwarding needs a small script to refresh it. The glasses must be on the same Wi-Fi as the
  PC (currently `192.168.1.2`), or use one of the setups in `ARCHITECTURE.md` section 6b.

Work:
- **Plan A:** install the Android app on WEBB OS. Add `GooltonSource` (the Goolton SDK camera)
  behind `FrameSource`, and adjust the popup to the real display (position, size, contrast).
- **Plan B (if the SDK blocks camera access):** the Android app runs on a paired Android phone,
  and the glasses connect over USB-C/DP. This is the only case where a phone is needed.
- **Check the glasses camera can focus on a leaf close up** (the plant model needs the leaf to
  fill the frame).
- Field test: inspect real leaves on a farm or in a greenhouse; measure Wi-Fi / hotspot
  reliability and latency. Record video there, to replay later through `FileSource`.

**Done when:** the wearer looks at a diseased leaf and sees the right disease popup on the
glasses, in a real field or greenhouse.
